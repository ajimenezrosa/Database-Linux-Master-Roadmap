# Introducción

En el capítulo anterior aprendimos a utilizar los **Comandos Ad-Hoc**, ideales para ejecutar tareas rápidas.

Sin embargo, administrar una infraestructura completa únicamente mediante comandos individuales no es práctico.

Imaginemos que debemos:

- Instalar Apache.
- Copiar un archivo de configuración.
- Crear un usuario.
- Reiniciar el servicio.
- Abrir el Firewall.
- Validar que el servicio esté funcionando.

Podríamos ejecutar seis comandos Ad-Hoc diferentes.

Pero existe una mejor alternativa.

Un **Playbook**.

---

# ¿Qué es un Playbook?

Un Playbook es un archivo escrito en **YAML** que contiene una o más tareas que Ansible ejecutará automáticamente.

En otras palabras:

> Un Playbook describe **el estado deseado** de un sistema, no los pasos manuales para llegar a él.

---

# Analogía

Supongamos que un administrador recibe el siguiente procedimiento:

```text
Instalar Apache

↓

Copiar configuración

↓

Iniciar servicio

↓

Habilitar inicio automático

↓

Validar funcionamiento
```

Cada vez deberá repetir exactamente los mismos pasos.

Con un Playbook:

```text
Playbook

↓

Ansible

↓

Todos los servidores

↓

Resultado idéntico
```

---

# Filosofía Declarativa

Ansible utiliza una filosofía **Declarativa**.

No indicamos:

```text
Haz esto

Luego aquello

Después esto otro
```

Indicamos:

```text
Quiero que Apache esté instalado.

Quiero que el servicio esté iniciado.

Quiero que esté habilitado.
```

Ansible decide qué acciones realizar.

---

# Automatización Imperativa vs Declarativa

## Imperativa

```text
Paso 1

↓

Paso 2

↓

Paso 3

↓

Paso 4
```

Se describe exactamente cómo realizar el proceso.

---

## Declarativa

```text
Estado Deseado

↓

Ansible calcula

↓

Realiza únicamente

los cambios necesarios
```

Los Playbooks son:

# Comandos Ad-Hoc vs Playbooks

| Comandos Ad-Hoc | Playbooks |
|-----------------|-----------|
| Una tarea | Muchas tareas |
| Uso inmediato | Automatización completa |
| Poco reutilizables | Altamente reutilizables |
| Soporte diario | Infraestructura |
| Sin documentación | Documentación implícita |
| Difícil mantener | Fácil mantener |
| Difícil compartir | Fácil compartir |

# ¿Qué es un Play?

Un archivo puede contener uno o varios **Play**.

Cada Play administra un conjunto de servidores.

Ejemplo

```yaml
- name: Configurar Web

  hosts: web
```

Otro Play

```yaml
- name: Configurar Base de Datos

  hosts: database
```

---

# ¿Qué es una Task?

Una Task representa una única acción.

Ejemplo

```yaml
- name: Instalar Apache

  dnf:

    name: httpd

    state: present
```

---

Cada Task debe ser:

- Clara.
- Independiente.
- Fácil de comprender.

# Importancia de la indentación

La indentación es obligatoria.

Correcto

```yaml
tasks:

  - name: Hostname

    command: hostname
```

Incorrecto

```yaml
tasks:

- name: Hostname

command: hostname
```

Ansible producirá un error.

# Interpretación

| Campo | Significado |
|--------|-------------|
| ok | Tarea ejecutada correctamente |
| changed | Hubo cambios |
| failed | Error |
| skipped | Omitida |
| unreachable | Sin conexión |

# ¿Qué significa changed?

Ejemplo

```text

```

---

# ¿Qué significa ok?

```text
ok=1
```

La tarea se ejecutó correctamente.

# Idempotencia

Es uno de los conceptos más importantes de Ansible.

---

## Definición

Un Playbook es **idempotente** cuando puede ejecutarse múltiples veces obteniendo siempre el mismo resultado.

---

# Ejemplo

Playbook

```yaml
- name: Instalar Apache

  dnf:

    name: httpd

    state: present
```

Primera ejecución

```text
Apache

No instalado

↓

Instalar

↓

changed
```

---

Segunda ejecución

```text
Apache

Ya instalado

↓

No hacer nada

↓

ok
```

---

# Beneficios

- Evita cambios innecesarios.
- Reduce riesgos.
- Ahorra tiempo.
- Facilita auditorías.
- Permite ejecutar Playbooks repetidamente.

---

```text

↓

↓

↓

↓

↓

```

# Primer Playbook Real

```yaml
---
- name: Instalar Apache

  hosts: web

  become: true

  tasks:

    - name: Instalar Apache

      dnf:

        name: httpd

        state: present

    - name: Iniciar servicio

      service:

        name: httpd

        state: started

        enabled: true
```

Las tareas siempre se ejecutan en orden.

```text

↓

↓

↓

Task 4
```

# Módulo dnf

Dentro de un Playbook.

```yaml

    name: vsftpd
```

# Playbook Completo

```yaml
---
- name: Configuración Inicial

  hosts: web

  become: true

  tasks:

    - name: Instalar Apache

      dnf:

        name: httpd

        state: present

    - name: Crear directorio

      file:

        path: /opt/web

        state: directory

    - name: Copiar página

      copy:

        src: index.html

        dest: /var/www/html/index.html

    - name: Iniciar servicio

      service:

        name: httpd

        state: started

        enabled: true
```

Un Handler es una Task especial que solamente se ejecuta cuando otra Task informa que realizó un cambio.

---

# Significado

| Campo | Descripción |
|---------|-------------|
| ok | Tareas ejecutadas correctamente |
| changed | Cambios realizados |
| failed | Errores |
| skipped | Tareas omitidas |
| unreachable | Host inaccesible |
| rescued | Errores recuperados mediante Rescue |
| ignored | Errores ignorados |

# Buenas Prácticas

- Utilizar Handlers para reiniciar servicios.
- Agrupar tareas relacionadas mediante Block.
- Utilizar Rescue para recuperar errores.
- Utilizar Always para limpieza.
- Asignar Tags descriptivos.
- Validar sintaxis antes de ejecutar.
- Ejecutar primero en Desarrollo.
- Utilizar nombres descriptivos.
- Mantener Playbooks pequeños y reutilizables.
- Versionar siempre con Git.
- Evitar el uso innecesario del módulo `shell`.
- Utilizar módulos específicos siempre que existan.
- Mantener un único objetivo por Playbook.
- Separar configuración por Roles cuando el proyecto crezca.
- Documentar cambios importantes.

# Resumen del Capítulo

En este capítulo aprendimos a desarrollar **Playbooks profesionales** con Ansible. Comenzamos estudiando la estructura básica de un Playbook y la filosofía declarativa, continuamos incorporando Variables, Facts, registros (`register`), condiciones (`when`) y bucles (`loop`) para crear automatizaciones dinámicas y reutilizables.

Finalmente, incorporamos mecanismos avanzados como **Handlers**, **Tags**, **Blocks**, **Rescue** y **Always**, que permiten construir automatizaciones más robustas, reducir interrupciones, manejar errores de forma controlada y ejecutar únicamente las partes necesarias de un Playbook. También revisamos prácticas recomendadas para pruebas, validación, auditoría y despliegues en Producción.

Con estos conocimientos ya es posible crear Playbooks seguros, mantenibles y escalables, preparados para administrar desde unos pocos servidores hasta infraestructuras empresariales de gran tamaño.

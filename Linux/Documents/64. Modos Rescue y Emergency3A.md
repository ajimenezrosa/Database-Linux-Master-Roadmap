# Introducción

No todos los fallos de arranque se deben a un error simple en:

```text
/etc/fstab
```

También pueden existir problemas relacionados con:

- Corrupción del sistema de archivos.
- Errores de hardware.
- Volúmenes LVM inactivos.
- Discos ausentes.
- Metadatos dañados.
- Contextos SELinux incorrectos.
- Unidades de `systemd` mal configuradas.
- Servicios que fallan repetidamente.
- Recursos críticos que no están disponibles.
- Particiones llenas.
- Inodos agotados.
- Directorios con propietarios incorrectos.
- Configuraciones de seguridad dañadas.

En estos casos, Rescue y Emergency proporcionan un entorno controlado para investigar y corregir el problema.

# Flujo general de recuperación avanzada

```text
El sistema no arranca
        │
        ▼
Acceder a Rescue o Emergency
        │
        ▼

        │
        ▼

        │

        │       └── /.autorelabel
        │
        └── Servicio crítico
                ├── status

                └── mask
```

# No reparar sin identificar el problema

Uno de los errores más peligrosos es ejecutar herramientas de reparación sin confirmar:

- El dispositivo correcto.
- El tipo de sistema de archivos.
- Si está montado.
- Si contiene datos críticos.
- Si existe respaldo.
- Si el fallo es lógico o físico.

Nunca ejecutes una reparación por intuición.

---

# Tabla de herramientas según el sistema de archivos

| Sistema de archivos | Herramienta principal |
|---|---|
| XFS | `xfs_repair` |
| ext2 | `e2fsck` o `fsck.ext2` |
| ext3 | `e2fsck` o `fsck.ext3` |
| ext4 | `e2fsck` o `fsck.ext4` |
| VFAT | `fsck.vfat` |
| Btrfs | `btrfs check` con precaución |
| Swap | `mkswap` si debe recrearse |

En entornos RHCSA modernos, XFS es especialmente importante porque suele ser el sistema de archivos predeterminado en RHEL.

# ¿Qué es `fsck`?

`fsck` significa:

```text
file system check
```

Es una interfaz que invoca la herramienta apropiada según el sistema de archivos.

Ejemplo:

```bash
fsck /dev/sdb1
```

Si el dispositivo es ext4, puede ejecutar internamente:

```text
fsck.ext4
```

o:

```text
e2fsck
```

---

# Consultar manuales

```bash
man fsck
```

```bash
man e2fsck
```

```bash
man fsck.ext4
```

---

# No utilizar `fsck` genérico sobre XFS esperando repararlo

En sistemas XFS, el comando adecuado es:

```bash
xfs_repair
```

Aunque `fsck.xfs` pueda existir, normalmente solo verifica que el sistema de archivos XFS se gestione con sus herramientas específicas.

```text
ext4 → e2fsck
XFS  → xfs_repair
```

# Nunca reparar un sistema de archivos montado

Antes de ejecutar una reparación:

```bash
findmnt /punto/de/montaje
```

o:

```bash
findmnt /dev/dispositivo
```

Ejemplo:

```bash
findmnt /dev/sdb1
```

Si está montado, desmonta:

```bash
umount /dev/sdb1
```

o:

```bash
umount /datos
```

---

# ¿Por qué no se repara montado?

Mientras está montado:

- El kernel puede escribir datos.
- Existen metadatos activos.
- Procesos pueden modificar archivos.
- La herramienta de reparación puede trabajar con información cambiante.
- Se puede agravar la corrupción.

---

```bash
fuser -vm /datos
```

También:

```bash
lsof +f -- /datos
```

Si existen procesos, detén el servicio correspondiente antes de desmontar.

# Paso 3: comprobar sin modificar

```bash
e2fsck -n /dev/sdb1
```

La opción:

```text
-n
```

responde “no” a todas las reparaciones y realiza una revisión no destructiva.

---

# Paso 4: reparar interactivamente

```bash
e2fsck /dev/sdb1
```

La herramienta puede preguntar si deseas corregir inconsistencias.

---

# Paso 5: reparación automática

```bash
e2fsck -p /dev/sdb1
```

La opción:

```text
-p
```

intenta reparar automáticamente problemas considerados seguros.

---

# Paso 6: forzar comprobación

```bash
e2fsck -f /dev/sdb1
```

Esto fuerza la revisión incluso si el sistema parece limpio.

---

# Combinación frecuente

```bash
e2fsck -f -p /dev/sdb1
```

Debe utilizarse con precaución y preferiblemente después de una revisión inicial.

# Interpretar códigos de salida de `e2fsck`

| Código | Significado |
|---:|---|
| 0 | Sin errores |
| 1 | Errores corregidos |
| 2 | Errores corregidos y se recomienda reiniciar |
| 4 | Errores no corregidos |
| 8 | Error operacional |
| 16 | Error de uso o sintaxis |
| 32 | Cancelado por el usuario |
| 128 | Error de biblioteca compartida |


---

# Caso especial: sistema raíz XFS

No puedes desmontar `/` mientras el sistema está utilizando esa raíz.

Para reparar la raíz debes iniciar desde:

- Medio de instalación.
- ISO de rescate.
- Otro sistema operativo.
- Entorno donde la raíz real no esté montada activamente.
- Máquina auxiliar, si el disco puede conectarse.

---

# Rescue no siempre permite reparar `/`

Aunque estés en Rescue, `/` sigue siendo el sistema raíz activo.

Por tanto:

```bash
xfs_repair /dev/mapper/rhel-root
```

no debe ejecutarse mientras `/` esté montado.

---

# Flujo correcto para reparar raíz XFS

```text
Arrancar desde ISO de rescate
        │
        ▼
No montar automáticamente la raíz
        │
        ▼
Activar LVM
        │
        ▼
Verificar dispositivo
        │
        ▼
xfs_repair -n
        │
        ▼
xfs_repair
        │
        ▼
Montar y verificar
```

---

# Opción `-L` de `xfs_repair`

En situaciones graves puede utilizarse:

```bash
xfs_repair -L /dev/dispositivo
```

Esta opción borra el log interno de XFS.

---

# Advertencia crítica sobre `-L`

`-L` puede provocar pérdida de cambios recientes o metadatos pendientes.

Debe utilizarse únicamente cuando:

- `xfs_repair` lo solicita.
- El log no puede reproducirse.
- Existe respaldo.
- Se comprende el riesgo.
- No existe una alternativa menos destructiva.

---

# Orden recomendado con XFS

```bash
xfs_repair -n /dev/dispositivo
```

Después:

```bash
xfs_repair /dev/dispositivo
```

Solo como último recurso:

```bash
xfs_repair -L /dev/dispositivo
```

# Diferencia entre corrupción lógica y error físico

## Corrupción lógica

Puede deberse a:

- Apagado abrupto.
- Error de software.
- Metadatos inconsistentes.
- Montaje defectuoso.
- Fallo durante escritura.

Puede corregirse con:

- `e2fsck`
- `xfs_repair`

---

## Error físico

Puede deberse a:

- Disco dañado.
- Sectores defectuosos.
- Controladora defectuosa.
- Cable defectuoso.
- Error de almacenamiento SAN.
- Fallo de RAID.
- Error de memoria.

Una herramienta de reparación lógica no corrige hardware dañado.

# LVM en entornos de recuperación

LVM permite organizar almacenamiento mediante:

```text
PV → VG → LV
```

Donde:

```text
PV = Physical Volume
VG = Volume Group
LV = Logical Volume
```

---

# Diagrama LVM

```text
Discos o particiones
        │
        ▼
Physical Volumes
        │
        ▼
Volume Group
        │
        ▼
Logical Volumes
        │
        ├── root
        ├── home
        ├── var
        └── swap
```

---

# Comandos fundamentales de LVM

| Comando | Función |
|---|---|
| `pvs` | Mostrar volúmenes físicos |
| `vgs` | Mostrar grupos de volúmenes |
| `lvs` | Mostrar volúmenes lógicos |
| `pvdisplay` | Información detallada de PV |
| `vgdisplay` | Información detallada de VG |
| `lvdisplay` | Información detallada de LV |
| `vgscan` | Buscar grupos |
| `lvscan` | Buscar volúmenes lógicos |
| `vgchange -ay` | Activar grupos |
| `vgchange -an` | Desactivar grupos |
| `lvchange -ay` | Activar un LV |
| `lvchange -an` | Desactivar un LV |

# Problema: un PV no está disponible

En `pvs` puede aparecer:

```text

```

- Disco eliminado.

- UUID de PV cambiado.
- Multipath no activo.
- Cabecera LVM dañada.
- Partición incorrecta.
- Controladora sin detectar el disco.

Restaurar metadatos:


# Advertencia sobre `vgcfgrestore`

No restaures metadatos al azar.

Una restauración incorrecta puede:

- Perder referencias a volúmenes.
- Sobrescribir cambios recientes.
- Dejar LVs inaccesibles.
- Empeorar el daño.

# No deshabilitar SELinux como primera solución

Evita editar:

```text
SELINUX=disabled
```

solo para ocultar un fallo.

La solución correcta suele ser:

- Restaurar contextos.
- Definir una regla persistente.
- Habilitar un booleano.
- Corregir permisos.
- Usar una ruta compatible.
- Crear una política específica.

---

# Probar temporalmente en Permissive

En una investigación controlada:

```bash
setenforce 0
```

Verificar:

```bash
getenforce
```

Después de probar:

```bash
setenforce 1
```

---

# Interpretación

Si el servicio funciona en Permissive, pero falla en Enforcing, existe una alta probabilidad de un problema SELinux.

Esto no significa que debas dejar el sistema en Permissive.

# Reetiquetado completo

Crear:

```bash
touch /.autorelabel
```

Reiniciar:

```bash
systemctl reboot
```

Durante el próximo arranque se realizará un reetiquetado amplio.

---

# Cuándo utilizar `/.autorelabel`

Puede ser apropiado cuando:

- Muchos contextos están dañados.
- Se restauró un sistema desde una copia.
- Se movieron archivos masivamente.
- Se modificó SELinux desde Rescue.
- Se recuperó una contraseña.
- Existen inconsistencias generalizadas.

---

# No utilizar reetiquetado completo innecesariamente

Puede tardar bastante y afectar la ventana de mantenimiento.

Si el problema está limitado a una ruta, utiliza:

```bash
restorecon -Rv /ruta
```

# Diferencia entre disable y mask

| Acción | Resultado |
|---|---|
| `disable` | Evita inicio automático |
| `stop` | Detiene ahora |
| `mask` | Impide cualquier inicio |
| `unmask` | Elimina la máscara |
| `enable` | Configura inicio automático |
| `start` | Inicia ahora |

# Cuándo enmascarar

Utiliza `mask` cuando:

- Una unidad se inicia como dependencia.
- El servicio provoca fallos graves.
- Se necesita impedir cualquier inicio temporal.
- Se está realizando una recuperación controlada.

# Ampliar LV y sistema de archivos

Para XFS:

```bash

/dev/rhel/var
```

La opción:

```text

```

intenta ampliar también el sistema de archivos.

# Advertencia

Antes de ampliar:

- Confirma el LV.
- Verifica espacio libre.
- Revisa respaldos.
- Comprueba el tipo de sistema.
- Evita ampliar el volumen equivocado.

---

# XFS no se reduce

XFS puede ampliarse, pero no reducirse de manera directa.

Esto es importante al planificar almacenamiento.

---

# Ext4 puede reducirse con condiciones

Ext4 puede reducirse, pero normalmente requiere:

- Desmontar.
- Ejecutar `e2fsck`.
- Reducir el sistema de archivos.
- Reducir el LV.

Es una operación de alto riesgo y no debe improvisarse durante una recuperación.

# Buenas prácticas de la Fase 3A

✔ Identificar el sistema de archivos antes de reparar.

✔ Desmontar antes de ejecutar herramientas de reparación.

✔ Utilizar `e2fsck` para ext4.

✔ Utilizar `xfs_repair` para XFS.

✔ Ejecutar primero modos no destructivos como `-n`.

✔ Evitar `xfs_repair -L` salvo último recurso.

✔ Revisar errores de hardware antes de asumir corrupción lógica.

✔ Verificar espacio e inodos.

✔ Activar LVM con `vgchange -ay`.

✔ Revisar copias de metadatos LVM antes de restaurar.

✔ Utilizar `restorecon` para contextos incorrectos.

✔ No deshabilitar SELinux permanentemente como solución rápida.

✔ Analizar AVC con `ausearch`.

✔ Deshabilitar servicios defectuosos antes de enmascararlos.

✔ Utilizar `mask` solo cuando sea necesario.

✔ Revisar dependencias de servicios y montajes.

✔ Ejecutar `sync` antes de reiniciar.

✔ Documentar cada cambio realizado.
